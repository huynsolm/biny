## 만든 이유

퍼블리셔로 일한 결과물은 있었지만, 프론트엔드로 넘어갈 수 있다는 걸 보여 줄 결과물은 없었습니다. 강의로 배운 React, Next.js, TypeScript를 실제로 써 보는 가장 빠른 방법이 포트폴리오를 직접 만드는 일이라고 판단했어요.

## 선택과 이유

- **Next.js 정적 생성**: 링크를 보냈을 때 미리보기가 나오고 빨리 열려야 하는 사이트라서, 빌드할 때 HTML을 만들어 두는 방식을 골랐습니다. 서버를 따로 운영하지 않아도 돼요.
- **프로젝트 내용은 MDX 파일**: 프로젝트를 추가할 때는 파일 하나만 더하면 됩니다. 지금 읽고 계신 글도 그런 파일이에요.
- **콘텐츠 형식 검증**: 필수 항목이 빠지거나 형식이 틀리면 빌드가 파일 이름과 항목 이름을 알려 주며 실패합니다. 검증 코드는 TypeScript로 쓰고 테스트를 붙였어요.
- **Tailwind 대신 CSS Modules와 CSS 변수**: 제 강점이 직접 짠 CSS라서, 그대로 드러나는 방식을 택했습니다. 색과 간격은 변수 한 곳에서 관리해요.
- **도면 노트 콘셉트**: 방안지 격자, 모노스페이스 라벨, 형광 포인트 하나로 마크업 구조를 눈으로 읽는 퍼블리셔의 습관을 디자인에 옮겼습니다.

## 겪은 문제

- **테스트 도구 설치 충돌**: Vitest를 설치하다가 `@types/node` 버전이 맞지 않아 막혔습니다. 강제 설치 옵션 대신, 실제 실행 환경인 Node 24에 맞춰 타입 버전을 올려 해결했어요.
- **모노스페이스와 한글**: 모노스페이스 글꼴은 한글을 못 그리는 경우가 많아서, 제목과 본문은 Noto Sans KR, 영문 라벨과 코드는 JetBrains Mono로 나눠 썼습니다.
- **명도 대비**: 색을 고른 뒤 글자와 배경, 격자선 위 글자의 대비를 공식으로 계산해 확인했고, 가장 낮은 조합이 5.09:1이었어요.

## 점검한 것

320px, 768px, 1280px 폭에서 홈과 상세 페이지의 가로 넘침을 쟀습니다. 키보드 이동 순서, 제목 레벨, 필터 버튼의 선택 상태 전달(`aria-pressed`)도 확인했고, 그 과정에서 상세 페이지에서 동작하지 않던 헤더 앵커 링크와 작은 터치 영역을 고쳤어요. 스크린 리더 테스트와 자동 접근성 점수 측정은 아직 하지 않았습니다.

## 만든 방식

초안 검토와 반복 작업에는 AI 코딩 도구(Claude Code)를 활용했고, 기술과 디자인 선택, 브라우저 검증은 직접 진행했습니다. 후보를 비교한 이유와 버린 대안은 `docs/decisions.md`에 남겼어요.

# 포트폴리오 사이트 설계

작성일: 2026-10-12

## 1. 목적과 배경

- **주 목적**: 취업/이직용. 보조 목적: 개인 브랜딩/기록.
- **작성자**: 현직 웹 퍼블리셔, 프론트엔드 개발자로 전환 희망.
- **관람자(가정)**: 채용 담당자/면접관. 링크로 1~2분 훑어봄.
- **보유 재료**: 공개 가능한 실무 퍼블리싱 작업물, JS/React 등 개인 프로젝트.
- **기존 포트폴리오와의 관계 (확정: 완전히 새 사이트)**: 기존 사이트(`team-library.biny.cloud/portfolio-recruiting-2026/`)는 퍼블리싱 역량 증명용이며 그대로 둔다. 새 사이트는 "퍼블리싱 경력 → 프론트엔드 전환" 스토리를 한 화면 흐름 안에서 보여준다. 기존 사이트의 콘텐츠(Gulp 템플릿, Ezmedicom, Yuni Wine, 브라우저 도구 3종, 작업 방식)는 재사용하되, 문구와 구성은 새로 쓴다. 기존 사이트는 "더 자세한 퍼블리싱 기록" 링크 한 줄로만 연결한다.
- **기술 경험**: React, Next.js, TypeScript (동영상 강의 수준).
- **성공 기준**: 1~2분 안에 "퍼블리싱 → 프론트엔드" 스토리와 대표 작업이 전달되고, 연락이 쉽다.
- **학습 요구사항**: 작성자가 "어떻게, 왜 그렇게 만들었는지" 설명할 수 있어야 한다. 사이트 자체가 프론트엔드 역량의 증거이다.

## 2. 사이트 구성

```
/                  메인 단일 페이지 (스크롤)
 ├ Hero            이름, 한 줄 소개, 연락 버튼
 ├ About           전환 스토리 + 기술 스택
 ├ Projects        카드 목록 (실무 퍼블리싱 + 개인 프로젝트, 필터)
 └ Contact         이메일, GitHub
/projects/[slug]   프로젝트 상세 (역할, 기술, 문제와 해결, 결과)
/log               기록 섹션 (초기에는 구조만)
```

이유: 메인 한 화면에서 핵심 파악, 상세 페이지는 "왜 그렇게 만들었나"를 보여주는 증거 자리, `/log`는 기록 목적을 위한 확장 여지.

## 3. 기술 구조

- **스택**: Next.js (App Router) + TypeScript, 정적 생성(SSG), Vercel 배포.
- **스타일링**: CSS Modules + CSS 변수 (퍼블리싱 역량이 그대로 드러나도록). Tailwind는 사용하지 않음.
- **콘텐츠**: `content/projects/*.mdx`, 프로젝트당 1파일. `/log`도 추후 같은 방식.
- **타입**: `lib/`에 프로젝트 메타데이터 타입을 정의하고 빌드 시 검증.

```
app/                 라우팅
components/          Hero, ProjectCard 등 역할 하나씩의 작은 컴포넌트
content/projects/    MDX 콘텐츠
lib/                 콘텐츠 로딩 함수, 타입
styles/              전역 스타일, 디자인 토큰
docs/decisions.md    기술/구조 선택 이유 기록
```

## 4. 디자인, 접근성, 배포

- **디자인 방향 (확정: B. 도면 노트)**: 방안지 격자 배경, 모노스페이스 글꼴 중심, 형광 포인트 색 하나. `margin`/`padding` 같은 구조 표시를 디자인 요소로 사용해 "마크업에서 로직으로" 스토리를 시각화한다. 필요하면 제목에만 세리프를 섞는 변형을 시안 단계에서 검토한다.
- **사람이 만든 느낌 원칙**:
  - 피한다: 보라/파랑 그라데이션, 유리 효과, 글로우, "중앙 정렬 Hero + 카드 3개" 템플릿, 이모지 아이콘 남발, 의미 없는 둥근 카드와 그림자 반복, "혁신적인/열정적인" 같은 뻔한 문구.
  - 지향한다: 색 2~3개와 글꼴 1~2개로 제한, 의도적 비대칭 레이아웃, 본인 말투와 실제 경험으로 쓴 소개 문구, 완성본뿐 아니라 고민 과정이 보이는 작업 소개, hover/포커스/줄 간격 등 디테일을 직접 다듬기.
  - 역할 분담: 색, 글꼴, 레이아웃 방향, 소개 문구 같은 취향 영역은 AI가 임의로 정하지 않고 선택지를 제시해 작성자가 고른다.
- 구체적 색/글꼴/레이아웃은 구현 중 시안 확인 후 결정.
- 반응형(모바일/태블릿/데스크톱), 접근성(시맨틱 태그, 키보드, 명도 대비) 필수.
- 다크 모드는 제외. 색을 CSS 변수로 관리해 추후 추가 가능하게 함.
- GitHub 저장소 + Vercel 자동 배포. 초기 도메인은 `*.vercel.app`.

## 5. 진행 순서와 학습 원칙

1. 프로젝트 생성, 폴더 구조, `docs/decisions.md`
2. 디자인 토큰과 전역 스타일
3. 메인 섹션 순서대로 (Hero, About, Projects, Contact)
4. MDX 데이터 연결, 상세 페이지
5. 반응형, 접근성 점검
6. 배포, `/log` 구조 개방

학습 원칙: 단계마다 코드 전에 "무엇을 왜" 설명, 작은 단위로 진행, 선택의 이유를 `docs/decisions.md`에 기록, 핵심 코드에만 "왜" 주석, 직접 해볼 부분은 안내 중심 옵션 제공.

## 6. 테스트 범위

단위 테스트는 최소(콘텐츠 로딩 등 핵심 로직). 화면은 빌드 성공, 반응형, 접근성 점검으로 확인.

## 7. 범위 밖 (YAGNI)

외부 CMS, 다크 모드, 커스텀 도메인, `/log` 실제 글 작성, 애니메이션 중심 효과.

# CMS Publishing QA Dashboard 설계

작성일: 2026-10-13

## 1. 목적과 배경

- **목적**: 채용 담당자가 "발행 전에 무엇을 어떤 기준으로 점검하는지"를 직접 눌러 보며 확인하게 한다. 사이트 `method` 섹션의 "키보드, 브라우저, 발행 기준으로 점검해요"를 동작하는 화면으로 보여 주는 개인 데모다.
- **성격**: 별도 개인 프로젝트. 실제 업무에 쓰인 도구가 아니고, 업무 성과의 근거도 아니다. 증거 맵에 이 프로젝트의 근거가 없으므로 "개인이 만든 데모"로만 표기한다.
- **데이터**: 실제 고객·병원 정보 없이 샘플 데이터와 브라우저 localStorage만 쓴다. 서버 저장, 외부 API, 로그인은 없다.
- **성공 기준**: 포트폴리오에서 링크로 열어 몇 분 안에 동작이 확인되고, 고객·병원·내부 도구 정보나 성과 수치가 어디에도 없다.

## 2. 범위

**포함**: 발행 점검 체크리스트 하나. 페이지를 샘플로 등록하고, 페이지마다 점검 항목의 상태를 기록하고, 요약을 본다.

**제외 (YAGNI)**: 이슈 로그 화면, HTML 붙여넣기 자동 점검, 계정/공유, 내보내기, 다국어, 서버 저장.

## 3. 위치와 구조

이 저장소의 `/qa-dashboard` 경로에 둔다(새 저장소를 만들지 않는다).

```
app/qa-dashboard/page.tsx            서버 컴포넌트. 제목, 안내 문구, <QaDashboard /> 렌더
components/QaDashboard.tsx           클라이언트 컴포넌트. 상태, localStorage, 화면
components/QaDashboard.module.css    스타일 (디자인 토큰만 사용)
lib/qa/checklist.ts                  점검 항목 정의, 샘플 페이지
lib/qa/state.ts                      순수 함수: 상태 변경, 요약, 발행 가능 판정
lib/qa/storage.ts                    직렬화와 검증 (localStorage 접근 자체는 컴포넌트가 담당)
tests/qa-state.test.ts               상태 로직 테스트
tests/qa-storage.test.ts             저장 검증 테스트
content/projects/cms-publishing-qa-dashboard.mdx   포트폴리오 사례
```

경계: `lib/qa/*`는 React와 브라우저 API를 모른다. 컴포넌트는 `lib/qa`의 함수를 호출하고 결과를 그리기만 한다.

## 4. 데이터 모델

```ts
type ItemStatus = "todo" | "pass" | "fail" | "na";

type ChecklistItem = { id: string; group: GroupId; label: string };

type QaPage = {
  id: string;
  name: string;
  note: string;                              // 한 줄 메모
  statuses: Record<string, ItemStatus>;      // key: ChecklistItem.id
};

type QaState = { version: 1; pages: QaPage[] };
```

**점검 항목** (사이트 방법 섹션과 프로젝트 점검 기준에서 가져온다. 확인하지 않은 브라우저 목록이나 점수는 넣지 않는다):

| 그룹 | 항목 |
|---|---|
| 시맨틱 | 제목 레벨이 순서대로 이어진다 / 이미지에 `alt`가 있다 / 주요 영역이 랜드마크로 구분된다 |
| 반응형 | 320px에서 가로 스크롤이 없다 / 터치 영역이 충분하다 |
| 키보드 | 탭 순서가 화면 순서와 같다 / 포커스 표시가 분명하다 |
| 브라우저 | 사용하는 주요 브라우저에서 확인했다 |
| 발행 | 링크가 동작한다 / 페이지 제목이 알맞다 |

**샘플 페이지**: "샘플 메인", "샘플 상담 안내", "샘플 오시는 길". 일반 이름만 쓴다.

**판정 규칙** (`lib/qa/state.ts`)
- 새 항목 상태는 `todo`다. 정의에 없는 항목 id는 `todo`로 취급한다.
- 페이지는 모든 항목이 `pass` 또는 `na`일 때만 "발행 가능"이다. `fail`이나 `todo`가 하나라도 있으면 아니다.
- 요약: 전체 페이지 수, 발행 가능 페이지 수, 선택 페이지의 통과/실패/미점검 개수.

## 5. 화면

- 위쪽: 제목, 상시 표시 안내문 "샘플 데이터예요. 이 브라우저에만 저장되고, 개인이 만든 데모예요." 그리고 요약.
- 본문: 페이지 목록(선택, 추가, 삭제)과 선택한 페이지의 체크리스트(그룹별, 항목마다 상태 선택)와 메모 입력.
- "샘플로 되돌리기" 버튼. 되돌리기 전에 확인을 받는다.
- 좁은 화면에서는 한 열로 쌓는다. 목록과 체크리스트가 가로 스크롤을 만들지 않는다.
- 스타일은 `styles/tokens.css`의 변수만 쓰고, 점선 테두리 같은 기존 카드 언어를 따른다. 그라데이션, 그림자 장식, 허위 지표는 쓰지 않는다.

## 6. 저장과 오류 처리

- localStorage 키 하나(`qa-dashboard:v1`)에 `QaState`를 JSON으로 저장한다.
- 읽을 때 `lib/qa/storage.ts`가 모양을 검증한다. JSON이 깨졌거나, `version`이 다르거나, 상태값이 4가지 밖이면 샘플로 시작한다. 이때 화면에 "저장된 내용을 읽지 못해 샘플로 시작했어요." 안내를 `role="status"`로 보여 준다.
- localStorage가 없거나 접근이 막힌 환경(`getItem`/`setItem` 예외)에서는 메모리 상태로만 동작하고, 저장하지 못한다는 안내를 한 번 보여 준다. 예외는 모두 try/catch로 감싼다.
- 서버에서 그린 HTML과 어긋나지 않도록, 첫 렌더는 샘플 상태로 하고 마운트한 뒤 저장값을 반영한다.
- 페이지 이름이 비어 있으면 추가하지 않는다. 페이지 수는 20개로 제한한다.

## 7. 접근성

- 상태 선택은 네이티브 `<select>`를 쓴다. 터치 영역은 최소 44px이다.
- 모든 컨트롤에 보이는 레이블이 있다. 포커스 표시는 기존 `:focus-visible` 스타일을 따른다.
- 요약이나 안내가 바뀌면 `role="status"` 영역에 문구를 넣어 스크린 리더에 알린다(프로젝트 필터 결과 안내와 같은 방식).
- 삭제와 되돌리기는 확인 후 실행한다. 확인은 `window.confirm`이 아니라 같은 화면의 확인 단계(버튼 두 개)로 구현해 포커스가 흐트러지지 않게 한다.
- 320px에서 가로 스크롤이 없다. `prefers-reduced-motion`을 지키며, 새 애니메이션은 추가하지 않는다.

## 8. 포트폴리오 연결

- `content/projects/cms-publishing-qa-dashboard.mdx`를 추가한다. `kind: frontend`, 스택은 실제 쓴 기술(Next.js, React, TypeScript, CSS Modules, Vitest)만 적는다.
- 본문은 문제 → 역할 → 구현 → 확인 순서로 쓴다. "별도 개인 프로젝트이고 샘플 데이터만 쓴다"를 분명히 하고, 본문 안에 `/qa-dashboard`로 가는 상대 링크를 둔다. (`liveUrl`은 `http(s)`만 허용하므로 쓰지 않는다.)
- 성과 수치, 실제 업무 적용, 점검 기준의 효과에 관한 표현은 쓰지 않는다.
- 목록 순서(`order`)는 5, 맨 뒤.

## 9. 테스트와 확인

- **Vitest (`lib/qa`)**: 초기 상태가 모두 `todo`, 상태 변경이 다른 페이지에 영향 없음, 발행 가능 판정(전부 통과, `na` 포함, `fail` 하나, `todo` 하나), 요약 개수, 페이지 추가/삭제/20개 제한과 빈 이름 거부, 직렬화 왕복, 깨진 JSON·잘못된 `version`·알 수 없는 상태값 거부.
- **브라우저 확인**: 상태 변경 후 새로고침 유지, 되돌리기, localStorage 비우기 후 샘플 시작, 320px 가로 스크롤, 키보드만으로 모든 조작, 44px 터치 영역.
- **빌드**: `npm test`, `npm run lint`, `npm run build`, `git diff --check`. `/qa-dashboard`가 정적 경로로 생성되는지 확인한다.
- 실제 스크린 리더 테스트와 접근성 점수 측정은 하지 않으며, 점수는 주장하지 않는다.

## 10. 열려 있는 확인 사항

- 사례 본문의 "문제" 문장은 작성자 확인이 필요하다. 증거 맵에 없는 내용이므로 "개인 학습 목적의 데모"라는 사실만 쓰고, 실제 업무 문제를 지어내지 않는다.
- `/qa-dashboard`는 홈 내비게이션에 넣지 않고, 사례 상세 페이지의 링크로만 연결한다.
